# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

DumTools is a collection of internal browser tools for **Dumortier (Groupe Fareneït)**, a French building-automation (GTB — *Gestion Technique du Bâtiment*) integrator. It is evolving from a set of standalone `.html` files into a **self-hosted internal SaaS** (see "Cible SaaS" below). The UI and all domain vocabulary are in **French**.

## Cible SaaS (en cours de construction)

Passage des outils HTML autonomes vers une plateforme unique, auto-hébergée sur une **VM Proxmox** interne, données **partagées entre tous** les collègues.

### Base client & numéro Why (transverse à TOUS les outils)

La **base client** (`/clients`, `src/lib/clients/`) est le pivot de la plateforme : depuis la fiche d'un client, on retrouve **tout ce qui a été produit pour lui à travers tous les outils** (présents et futurs). Deux conventions s'appliquent donc à **chaque outil** :

Depuis le 2026-08-12, `Client` porte aussi son **identité postale**
(`adresse/codePostal/ville/telephone/email`) et **N contacts** (`ContactClient` :
civilité, nom, fonction, email, tél, `principal`, `actif`) — voir
[`docs/DEVIS.md` §24](docs/DEVIS.md). Un document qui SORT chez le client s'en
sert pour **pré-remplir** son destinataire, jamais pour le remplacer : le
référentiel vit, le document fige. ⚠️ `renommerClient` resynchronise le
`clientNom` dénormalisé de **tout** ce qui en porte un (grep `clientNom` dans
`schema.prisma`) — l'oubli de `Devis` et `Visite` laissait l'ancien nom sur la
page publique que le client a sous les yeux.

1. **Rattachement au client** — l'entité principale de l'outil porte `clientId String?` (FK → `Client`, `onDelete: SetNull`) **en plus** du libellé dénormalisé `clientNom`. Au save, l'action de l'outil résout le nom saisi en id via `resoudreClientId(nom)` (`src/lib/clients/queries.ts`), qui **crée le client** au besoin (upsert par nom). Renommer un client resynchronise les `clientNom` liés.
2. **Numéro Why** — l'entité porte `numeroWhy String?` : la **référence de l'affaire / du chantier dans WhySoft** (notre CRM). Un document = une affaire Why. Champ éditable dans chaque éditeur, affiché en colonne sur les index et sur la fiche client.

**Agrégation multi-outils** — chaque outil expose `listerPourClient(clientId): Promise<ClientArtefact[]>` (dans son `queries.ts`) et l'enregistre dans `PROVIDERS` de `src/lib/clients/providers.ts`. La fiche client `/clients/[id]` compose tous les providers (triés par date). `ClientArtefact` (`src/lib/clients/types.ts`) = `{ id, titre, href, numeroWhy, updatedAt, resume }`.

> **Ajouter un futur outil à la base client** : (a) `clientId` + `numeroWhy` sur son entité (`schema.prisma`) ; (b) `resoudreClientId` + persistance `numeroWhy` dans son action de save ; (c) champ `numeroWhy` + combobox client dans son éditeur ; (d) `listerPourClient` dans son `queries.ts` ; (e) une ligne dans `PROVIDERS`. Rien d'autre — la fiche client le prend en compte automatiquement.
>
> **Idem pour la fiche Affaire** (2e pivot, [`docs/AFFAIRES.md`](docs/AFFAIRES.md)) : ajouter `chantierId` sur l'entité, résoudre via `resoudreChantierId(numeroWhy, clientId, nom)` au save, exporter `listerPourChantier`, et une ligne dans `PROVIDERS` de `src/lib/chantiers/providers.ts`.

## Domain glossary (needed to read the code)

- **GTB** — building management system. **E/S** = I/O (*entrées/sorties*). **automate** = controller. **module d'extension** = expansion module. **chantier** = worksite/project. **point** = a single I/O point.
- **I/O types**: `AI` (analog in), `DI` (digital in), `AO` (analog out), `DO` (digital out), `COM` (bus/communication — excluded from physical I/O totals).
- **Distech Controls ECLYPSE** controllers: `ECY-300/303/400/450/600/650/PTU/S1000E`. Some models have *integrated* I/O on the controller itself; others rely purely on extension modules.
- **`.gfx`** — a Distech Controls program file. It is a **ZIP archive of XML**, parsed with bundled JSZip + `DOMParser`.

## Les outils historiques (`existant/`)

`existant` ("existing") holds the legacy standalone tools — kept as functional spec while they are rewritten into the SaaS.

### `ListePts_GTB.html` — points-list editor ("Liste de Points GTB")
Editable table where each row is a **point** or a **section** header. A point has a name, free-text note, and per-type I/O counts. Features: client combobox backed by an embedded `DB` object (client list + point templates), drag-and-drop row reorder, insertable templates, live totals, and a **paginated A4 print/PDF view** (`buildPrintPages` etc.) with per-page subtotals and a grand total.
- State model: `rows = [{id, kind:'point'|'section', name, free, io:{AI,DI,AO,DO,COM}, sectionName}]`.
- Legacy persistence: `localStorage['gtb_listepts']`. Palette CSS de référence (voir `:root`) : `--brand-blue:#2b3a8f`, `--brand-orange:#ee7d1b`, couleurs E/S `--ai/#1f6feb --di/#b4690e --ao/#7b41c9 --do/#1a8a4a --com/#0d8c97`.

### `Affectation_ES_depuis_GFX.html` — I/O assignment generator ("Générateur E/S Distech depuis GFX")
The larger, more complex tool (~4 MB — inlined JSZip, Mozilla PDF.js, and hardware photos). It **imports a Distech `.gfx` program and/or an electrical-schematic PDF** and auto-generates the I/O assignment document.
- Two import pipelines, both entirely client-side:
  - **GFX** (`buildGfxModules`, `detectControllerFromGfxXml`, `inferModulesFromPointResources`, `normalizeGfxIntegratedArchitecture`, …): unzip → parse XML → detect controller model, integrated I/O, and extension modules.
  - **PDF** (`extractPdfModulePage`, `associatePdfLabels`, `detectPdfControllerModel`, `ptu*`/`ecy*ControllerPoints`, …): PDF.js text extraction with heavy geometric/positional heuristics to recover point labels and folio references from schematic drawings. This is the most heuristic, fragile part of the codebase.
- Hardware catalog: `CONTROLLER_CATALOG`, `MODULE_IMAGE_DATA`, `CONTROLLER_IMAGE_DATA` (base64 images) drive both the config UI and the printed diagrams.
- Tabbed SPA (`showTab`, `data-tab` = `dashboard|project|modules|inputs|outputs|tests|preview`) with a **commissioning/test tracker** (`buildTestReport`, per-point status + multi-line comments) and a **print preview** producing the full document (cover, controller page, one page per module).
- Central state: `project` + `MODULES`. Legacy persistence: `localStorage['affectation-es-distech-v25-reseaux-editables']`.

## Working in this codebase

- Keep UI strings and identifiers in **French** to match the surrounding code and the users.
- The `.gfx`/PDF parsing logic is worth preserving when rewriting — port it to TypeScript modules (`src/lib/`) rather than reinventing the heuristics.
- Le logo officiel est dans `logo/Logo FARENEIT DUMORTIER.png` (copié en `public/logo-dumortier.png`).

## Notes techniques (pièges des versions récentes)

- **Design system (charte)** : 3 étages — `src/styles/primitives.css` (les seuls #hex + courbes/durées d'animation) → `src/styles/semantic.css` (rôles, densité, thème sombre en override unique) → `src/app/globals.css` `@theme inline` (Tailwind v4). Les composants n'utilisent QUE des utilitaires sémantiques (`bg-brand`, `text-io-ai`, `border-border`…). Reskin = éditer l'étage sémantique.
  - **Direction « cartouche & rail »** : l'interface emprunte le vocabulaire du schéma électrique. Chaque écran s'ouvre sur un **cartouche** (`<Cartouche>` de `@/ui`) — estampille, titre, état, pavé de champs de référence — plutôt qu'un `h1` + paragraphe. Classes de signature dans `globals.css` : `.cartouche` / `.cartouche-champs`, `.stamp` (libellé en petites capitales), `.ref` (référence technique en mono : n° Why, borne, folio), `.rule-signal` / `.rule-signal-v` (filet des 5 signaux AI·DI·AO·DO·COM), `.voile-brand` (lumière douce sur une grande surface marine), `.rail`. **Pas de motif de fond** : le plan de travail est une surface unie légèrement creusée (`--page`), les blocs blancs s'y posent comme des feuilles. L'ancienne trame « papier quadrillé » a été retirée — à petite échelle elle ne lisait pas, à grande échelle elle salissait.
  - **Bâti sombre, plan de travail clair** (façon logiciel de CAO). Au bureau : **rail d'icônes** de 64px (`rail.tsx`). Au téléphone (< 768px) : **barre d'onglets en bas** (`barre-mobile.tsx`) — 4 destinations au pouce + feuille « Plus » (configuration, densité, thème, déconnexion). Les deux lisent la même source, `nav.ts`. En haut, la **barre de chrome** (`barre-chrome.tsx`) annonce en permanence l'écran courant.
    - ⚠️ Un composant **serveur** ne peut pas passer une entrée de nav à un composant **client** : les icônes Lucide sont des fonctions, la sérialisation échoue. Chaque composant client appelle `entreesNav()` lui-même.
  - **Contexte d'écran** : `<Cartouche>` alimente automatiquement la barre de chrome (via `<TitreEcran>`). Quand `titre` est du JSX, passer aussi `titreTexte`. Les écrans-outils sans cartouche (éditeurs plein écran) rendent `<TitreEcran>` directement.
  - **Pas de carte flottante** : les structures sont à angles droits, au trait fin, **sans ombre** — `.bloc` (bloc simple), `.bloc-entete`, `.planche` (grille de blocs bord à bord qui partagent leurs filets, colonne bornée par `minmax(0,1fr)`). Les ombres restent réservées à ce qui survole vraiment le plan : menus, popovers, listes déroulantes.
  - **Les chiffres se lisent de loin** : `.chiffre` / `<Chiffre>` + `<RangeeChiffres>` (rangée de compteurs bord à bord). Un `valeur` **numérique** se cale comme une aiguille au montage (`<Compteur>`, 600 ms, une seule course ; les valeurs composées type « 12/40 » restent fixes). `<JaugeES>` affiche la répartition AI·DI·AO·DO·COM — ordre **fixe**, segments qui poussent depuis zéro (`.jauge-anim`), et chaque segment porte son sigle : les teintes DO (vert) et COM (turquoise) sont trop proches pour porter l'information seules, mais elles sont contractuelles (imprimées sur les documents client) et ne doivent pas changer.
  - **Le signal de l'outil** : chaque outil du registre porte un `signal` E/S (`SignalOutil` dans `registry.ts`) — Projet GTB=AI bleu, Visites=DI ambre, Notes=AO violet, Documents=DO vert, Wiki=COM turquoise ; l'affaire (le pivot) et les référentiels portent le laiton. `classeSignal(teinte)` pose `.signal-*`, qui réécrit `--signal` pour tout le sous-arbre → `text-signal`, `bg-signal/12`, `border-signal`. Sur le **bâti sombre** (rail, barre de chrome, barre mobile), utiliser la variante **`-lift`** (`text-signal-lift`) : l'ocre DI y serait illisible. `teinteDeRoute(pathname)` (`nav.ts`) donne la teinte de l'écran courant — c'est elle qui allume le filet sous la barre de chrome à chaque navigation. La couleur ne porte jamais l'information seule : elle double toujours une icône et un libellé.
  - **LED & synoptique** : `.led` (+ `.led-on` sous tension, `.led-cur` qui respire, `.led-na` non câblé) et `.synoptique` / `.syn-etape` / `.syn-vive` (piste pleine tant que le courant passe, pointillée au-delà ; verticale au téléphone, horizontale dès 640px, `--syn-n` = nombre d'étapes). `.syn-courant` fait passer la lueur **une seule fois** à l'ouverture — c'est le seul endroit de l'appli où on se le permet. Deux emplois : `<FriseCycle>` (7 jalons de la fiche Affaire) et `<SynoptiqueMini>` (5 voyants du cycle commercial, en ligne de tableau, toujours accompagné de `<EtatBadge>`).
  - **Une seule surface marine par écran** : `.plaque-brand` (dégradé + voile de lumière en une déclaration). ⚠️ Ne jamais combiner `.bg-brand-gradient` et `.voile-brand` sur le même élément — les deux écrivent `background-image`, la seconde gagne et on obtient un voile sur du blanc.
  - **Typographie** : IBM Plex Sans (texte) + Archivo (`font-display`, titres & estampilles) + IBM Plex Mono (`font-mono`, repères). Déclarées dans `src/app/layout.tsx` sous `--font-sans-app` / `--font-display-app` / `--font-mono-app`.
  - **Densité** : `data-density="confort|compact"` sur `<html>` pilote `--root-size` (16,5px / 14,75px) ; tout étant en rem, l'interface entière suit. Réglage utilisateur dans la barre de chrome et dans la feuille « Plus » du téléphone (`DensityToggle`), mémorisé en `localStorage` et appliqué avant le premier rendu par le script anti-flash du layout racine — comme le thème.
  - **Mouvement** : une seule idée, « la mise sous tension ». Utilitaires `.anim-rise` (entrée d'un bloc), `.anim-page` (entrée de page, via `TransitionPage` qui remonte le contenu à chaque changement de route), `.stagger` (cascade courte, plafonnée au 10ᵉ enfant), `.anim-sweep` (filet laiton), `.anim-rail`, `.skeleton`, `.press`. Tout est neutralisé sous `prefers-reduced-motion`.
  - **Kit** : `@/ui` exporte aussi `EnteteBloc` (barre de titre POSÉE DANS un `.bloc` : icône au signal, titre, compteur, mention, actions à droite — c'est la grammaire de l'accueil et de la fiche Affaire), `EnteteSection` (variante à l'ancienne, titre au-dessus du cadre), `Repere` (un chiffre de consultation sur une ligne, à côté d'un titre ; le gros `Chiffre` reste pour ce qui se lit de loin), `EtatVide` (états vides « actifs » : ils proposent l'action), `Dessin`, `Stat`, `Kbd`, `Skeleton`. Les listes utilisent `.data-card` + `.data-table` (+ `.table-cards` pour le repli mobile) — **jamais** une `<table>` re-stylée à la main.
  - **Chacun règle sa table** : `useColonnes` + `<ReglageColonnes>` / `<ColgroupColonnes>` / `<EnteteColonnes>` (`src/ui/colonnes.tsx`, [`docs/DEVIS.md` §18.2](docs/DEVIS.md)) — largeur, ordre et visibilité des colonnes, par poste (`localStorage`, comme le thème et la densité), sur `.data-table--reglable`. Trois choix portent tout : **le défaut doit être bon** (colonnes d'appoint `masqueeDefaut`, « Réinitialiser » efface l'entrée de stockage au lieu d'y écrire le défaut) ; **une colonne `souple` prend la place qui reste** et `--tbl-min` est un `calc()` des variables de largeur → la table remplit son cadre et ne défile que si les colonnes fixes ne tiennent plus, **sans mesure JS** ; **le tirage n'écrit que dans le DOM**, l'état n'est figé qu'au lâcher — d'où plusieurs tables (les lots d'un devis) alignées sur un seul réglage, en héritant des variables du conteneur. Réglage lu en `useSyncExternalStore` (pas de divergence d'hydratation, autres onglets suivis). ⚠️ Le conteneur se retrouve par `data-colonnes`, **jamais par une ref** — une ref rendue par un hook fait crier le lint React dès qu'on passe l'objet à un composant (même piège que `useLecteurCode`). Sous 640 px `.table-cards` reprend la main : les largeurs sont neutralisées, l'ordre et les colonnes masquées valent toujours.
  - **Les filtres se souviennent du poste** : `src/lib/filtres-url.ts` — `useSyncUrl(filtres, cle)` + `useReprendreFiltres(cle, noms, reprendre)`, branchés sur les **10 écrans de liste** (affaires, projets GTB, listes de points, clients, notes, devis, rayon, wiki simple et avancée, réponses de formulaire — cette dernière avec une clé **par formulaire**). L'URL restait la seule mémoire : elle couvre le retour par la flèche et le `?retour=` d'une fiche, mais revenir par **le rail, l'accueil, ⌘K ou un favori** amène sur une adresse nue et tout retombait au défaut — l'agacement quotidien du tableau de bord des affaires. Deux étages, donc : l'**adresse** décrit la vue (partageable), le **`localStorage`** retient le dernier réglage (par poste, comme le thème, la densité et `useColonnes`). Trois règles portent tout : **l'adresse gagne EN BLOC** — un seul filtre de l'écran présent et la mémoire se tait, sinon un souvenir invisible viderait un lien reçu (d'où `sans-affaire` déclaré dans les `noms` de l'index Projet GTB, c'est un paramètre d'ENTRÉE) ; **« Réinitialiser » efface l'entrée** au lieu d'y écrire le défaut, et c'est automatique — le réglage par défaut produit une query string vide, qui déclenche la suppression ; ⚠️ **la reprise vit dans un EFFET**, jamais dans un initialiseur de `useState` — ceux-ci tournent aussi côté serveur, où `localStorage` n'existe pas, et les y brancher ferait diverger l'hydratation (on paie une image au défaut, invisible à l'usage). `ETATS_VUE_DEFAUT` est passé à **Commande + En cours** : ce qui est engagé, pas les chiffrages en attente de réponse.
  - **Les vides sont dessinés** : `<Dessin>` (`src/ui/dessins.tsx`) — six pièces du monde GTB au trait fin (`bornier`, `automate`, `armoire`, `carnet`, `touret`, `pochette`). Préférer `<EtatVide dessin="…">` à `icone={…}`. Règles de la série : viewBox `0 0 120 84`, trait 1.25, aucun remplissage, **un seul** détail en laiton par dessin, pointillés = ce qui manque justement.
- **Fil d'activité & attribution** : `Chantier`, `AffectationProjet`, `Note`, `Visite`, `WikiPage` portent `updatedById` = auteur de la dernière modification **humaine** (relations Prisma nommées `*Creee`/`*Modifiee`). Les server actions le posent dans le même `data` que l'écriture (donc atomique avec les gardes de version des notes/wiki) ; côté MCP, `brancherActeur()` (`mcp/data.mts`, branché par `mcp/server.mts`) fournit l'utilisateur du jeton. **Les écritures techniques n'y touchent pas** : synchro kDrive, propagation de dénormalisation (renommage client / modification d'affaire), réordonnancement de fratrie wiki, cascade de rubrique, scripts de backfill. Agrégé par `src/lib/activite/queries.ts` → carte « Activité récente » de l'accueil (repli sur `createdBy` pour les lignes antérieures).
- **« C'est bon, tu l'as déjà fait » — l'arrêt** (`src/lib/chantiers/arret.ts`) : la frise des 7 jalons est entièrement DÉRIVÉE et c'est sa force, mais elle répond à « où en est l'affaire ? », pas à « **est-ce que j'ai fini d'y toucher ?** ». Un automate à 12 points sur 40 ressemble trait pour trait à une étude finie, et un besoin en matériel vide se lit pareil qu'on n'ait rien commencé ou qu'il n'y ait rien à commander : cette réponse-là est une **décision humaine**, la seule chose qu'aucun calcul ne sait produire. D'où `AffectationProjet.arreteLe/arreteParId` (par automate : en multi-automate l'un peut être fini et l'autre non) et `Chantier.bomArreteeLe/bomArreteeParId` (le besoin est au niveau affaire). **Pourquoi cette case ne ment pas** : elle est DATÉE et confrontée au contenu — `etatArret(arreteLe, referenceLe)` rend `ouvert` / `arrete` / **`retouche`**, ce dernier étant *constaté*, jamais choisi. ⚠️ **Corollaire non négociable** : poser l'arrêt passe par un **UPDATE SQL brut** avec `now()` — un `prisma.update()` bousculerait `updatedAt`, et tout arrêt serait « retouché » dans la milliseconde qui suit (et `updatedById` ferait remonter l'affaire au fil d'activité pour un clic qui n'a rien produit) ; l'horloge doit être celle de la **base**, la même que celle des `updatedAt` comparés. ⚠️ Le besoin en matériel étant **dérivé**, il n'a pas de date à lui : son repère est `max(updatedAt des projets, bomToucheeLe)`, et `bomToucheeLe` est tamponné par les **4** actions qui touchent la BOM (`marquerBomTouchee`, `src/lib/chantiers/arret-serveur.ts`) — **y compris celles qui SUPPRIMENT** : retirer une ligne manuelle ou décocher « hors fourniture » ne laisse aucune trace dans sa propre table, et sans ce tampon le besoin resterait vert alors qu'il vient de maigrir. Les changements de **référentiel** (nomenclature, `sansMateriel`) restent hors du tampon : ils valent pour toutes les affaires, les estampiller toutes n'aurait pas de sens. Le clic est un **cycle à trois temps** — depuis « retouché » il ré-arrête, il ne rouvre pas.
